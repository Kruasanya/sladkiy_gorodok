# Модель 1. Прогноз спроса/заказов

> Статус: рабочая версия есть (boosting, 6 фич), не финальная — см. план дальнейших шагов внизу.

## Что модель будет делать

Предсказывать, сколько единиц каждого товара продастся (отгрузится сетям) на следующей неделе.
Прогноз на уровне `товар × неделя` (не по магазину — при 3 актуальных товарах и текущем объёме
истории дробить по магазинам/сетям рано). Пробовали день × товар — формально строк в 8 раз
больше, но отгрузки идут пачками 2-4 раза в неделю, и на дневных тестовых окнах WAPE становился
нестабильным. Неделя соответствует реальному ритму отгрузок, поэтому она основная.

Зачем: это первый и главный вход для модели 3 (рекомендация объёма производства, см.
`../../модели_план.md`) — без оценки будущего спроса нельзя ни избежать перепроизводства
(порча, занятые мощности), ни дефицита (пропущенные продажи, недовольство сетей).

## Данные

Источник: `Данные/Итоговые таблицы/sales_by_counterparties.parquet`.

- Фильтр: `sales_doc_type == "Реализация"` (без `"Корректировка реализации"` — возвраты это
  отдельная модель 2, не должны путать таргет спроса).
- Группировка: `nomenclature` (сырое название из 1С) → потом джойн на
  `Обучение моделей/Справочники/справочник_товаров_шаблон.csv` по `nomenclature_raw`, чтобы
  получить `общее_название` и отфильтровать `актуальность == "да"` — неактуальные товары
  (Мечта, Неженка, Сладкоежка, Сувенир, Шакер-Чурек — по справочнику уже помечены `нет`)
  прогнозировать не нужно, история по ним есть, но производство их не выпускает.
- Гранулярность по времени: неделя, agg по `sale_date`, таргет — сумма `quantity` за неделю по
  товару. Недели без продаж заполняются нулями в пределах диапазона первая..последняя продажа.
- Доступный период: май 2025 — июнь 2026 (~14 месяцев / ~50 недель на товар).

## Что уже решено в ноутбуке

1. **EDA**: длина истории, доля недель с продажами по товару (85-88%), визуальный тренд.
2. **Метрика оптимизации**: WAPE — основная (устойчива к разному масштабу товаров), MAE — для
   интерпретируемости в штуках и как проверка, что WAPE не искажает картину (см. оговорку ниже).
3. **Бейзлайны**: наивный прогноз (`lag_1`), скользящая средняя за 4 недели.
4. **Тип модели и валидация**: time-based split (последние 8 недель — тест) + rolling-origin CV
   на 3 окнах для проверки устойчивости. Сравниваем gradient boosting и линейную регрессию.
5. **Фичи**: после отбора по permutation importance — `lag_1`, `lag_2`, `roll_mean_4`,
   `share_светофор`, `week_of_year`, `праздничные_дни_в_месяце` (полный список фич-кандидатов
   и почему отброшены остальные — см. промежуточные итоги ниже).

## Структура папки

- `прогноз_спроса.ipynb` — единый ноутбук: загрузка → EDA → фичи → бейзлайны → сравнение моделей.

## Промежуточные итоги (после первых прогонов)

- **Гранулярность — неделя, не день.** Пробовали день: формально строк в 8 раз больше (~1000
  против 130), но отгрузки идут пачками 2-4 раза в неделю (доля дней с продажами 23-38%), и на
  дневных тестовых окнах WAPE становился нестабильным (>1 даже у бейзлайнов) — сумма фактических
  продаж в знаменателе схлопывалась почти до нуля. Неделя соответствует реальному ритму отгрузок.
- **На недельной гранулярности при 106 строках train / 13 фичах ML пока проигрывает бейзлайну:**

  | Подход | WAPE | MAE |
  |---|---|---|
  | **moving_average_4** | **0.669** | 624 |
  | naive (lag_1) | 0.735 | 686 |
  | hist_gradient_boosting | 1.059 | 989 |
  | linear_regression | 1.621 | 1513 |

  Текущая рабочая модель — скользящая средняя за 4 недели. ML (линрег, бустинг) переобучался:
  слишком мало строк (106 train) на число фич (13).

- **После сокращения фич до 6 (по permutation importance) бустинг обогнал бейзлайн:**

  | Подход | WAPE | MAE |
  |---|---|---|
  | **hist_gradient_boosting (6 фич)** | **0.652** | 608 |
  | moving_average_4 | 0.669 | 624 |
  | naive (lag_1) | 0.735 | 686 |
  | linear_regression (6 фич) | 0.748 | 699 |

  Сокращённый набор: `lag_1`, `lag_2`, `roll_mean_4`, `share_светофор`, `week_of_year`,
  `праздничные_дни_в_месяце`. Убраны (по нулевой/отрицательной важности при 13 фичах):
  `срок_годности_дней` (дублирует товар при всего 3 SKU), `общее_название` (категориальный
  признак товара мешал — создавал лишние разбиения на малых данных), `roll_mean_8`, `lag_4`,
  `roll_std_4`, `price_per_unit`, `share_маяк` (дублирует `share_светофор`, сетей всего две).

  Главный сигнал по важности — `share_светофор` (доля продаж через сеть Светофор за последние
  4 недели), затем `lag_1`/`lag_2`.

- **Rolling-origin CV (3 окна по 8 недель) подтвердила устойчивость выигрыша boosting:**

  | Подход | средний WAPE | std по фолдам |
  |---|---|---|
  | **boosting (v2, 6 фич)** | **0.624** | 0.041 |
  | moving_average_4 | 0.655 | 0.015 |
  | naive (lag_1) | 0.768 | 0.029 |
  | linear_regression (v2, 6 фич) | 0.834 | 0.209 |

  Boosting обгоняет `moving_average_4` во всех трёх фолдах, не только на последнем окне — выигрыш
  не случайность одного разбиения. Linear regression нестабильна (std=0.209, на самом маленьком
  train проваливается до WAPE 1.07) и не подходит как кандидат при таком объёме данных.

  **Текущий вывод: boosting (6 фич: `lag_1`, `lag_2`, `roll_mean_4`, `share_светофор`,
  `week_of_year`, `праздничные_дни_в_месяце`) — рабочая модель**, устойчиво обгоняет лучший
  бейзлайн и по среднему WAPE (0.624), и по среднему MAE (810 шт.). Не финал — следующие
  кандидаты на улучшение: подбор гиперпараметров бустинга, таргет как отклонение от скользящей
  средней вместо абсолютного объёма, больше данных (товаров/истории) по мере накопления.

  **Важная оговорка по метрике:** WAPE и MAE по отдельным фолдам ранжируют фолды по-разному —
  fold 2 выглядел "лучшим" по WAPE (0.577 у boosting), но по MAE он хуже fold 0 (854 против 608).
  Причина — разный знаменатель WAPE (сумма фактических продаж за окно: 22 404 в fold 0 против
  35 513 в fold 2, в основном из-за резкого падения продаж "Кекс с изюмом" в последних неделях).
  При сравнении отдельных окон друг с другом нужно смотреть на MAE, а не только на WAPE — иначе
  можно сделать ложный вывод "модель точнее на старых данных", когда на самом деле дело в
  размере знаменателя.

## Планы дальше

Приоритет по убыванию ожидаемой отдачи:

1. **Подбор гиперпараметров бустинга** (`num_leaves`, `n_estimators`, `learning_rate` сейчас
   взяты на глаз) — через rolling-origin CV из раздела 13, не обычный k-fold (перемешает время).
2. **Таргет как отклонение от тренда**, а не абсолютный объём: `quantity / roll_mean_4` вместо
   `quantity` — должно быть проще выучить на малых данных, чем абсолютные числа разного
   масштаба между товарами.
3. **Ансамбль бейзлайна и модели**: `(moving_average_4 + boosting) / 2` — дёшево проверить,
   ошибки разных подходов иногда компенсируют друг друга.
4. **Внешние объясняющие переменные**: график промо-акций сетей (Светофор/Маяк), если такие
   данные есть — текущая модель пытается угадать скачки продаж только по лагам, хотя реальная
   причина может быть в акции.
5. **Больше данных — главный реальный рычаг, не зависящий от модели.** Как только в справочнике
   появятся новые `актуальность = да` товары или накопится больше истории — повторить весь
   ноутбук: с большим train ML обычно выигрывает у бейзлайна с большим отрывом, чем сейчас.
6. **Передать модель в продукт** (см. `../../модели_план.md`, раздел "Поставка в продукт"):
   обернуть итоговый пайплайн (build_features → boosting_v2.predict) в скрипт, который пересчитывает
   прогноз раз в неделю и пишет результат в таблицу для дашборда и для модели 3 (рекомендация
   объёма производства).
