\chapter{Загрузка данных}
\label{ch:data}

Исходные данные для анализа поступают из учетной системы предприятия в виде выгрузок Excel и обрабатываются набором Python-пайплайнов (директория \texttt{Данные/Пайплайны обработки данных}), которые приводят разнородные отчеты к трем нормализованным таблицам: продажи по контрагентам, оплаты по контрагентам и банковские операции. Каждый пайплайн читает исходные \texttt{.xls}/\texttt{.xlsx}-файлы из своей папки-источника, разбирает их структуру построчно и сохраняет результат в формате Parquet, CSV и XLSX.

\section{Зачем нужна предварительная подготовка данных}

Перед тем как переходить к классификации операций, построению управленческого ДДС и прогнозным моделям (главы~2--4), исходные выгрузки нужно превратить в данные, на которые можно положиться. Это не техническая формальность, а отдельный этап с прямым экономическим смыслом: бизнес-решения принимаются на основе агрегатов (суммы по периодам, доли категорий, остатки по контрагентам), а любая ошибка на уровне строки — задвоенная операция, потерянный платеж, неверно распознанная дата — искажает именно те цифры, на которые в итоге смотрит собственник.

Базовая подготовка данных в проекте решает три задачи:

\begin{enumerate}
  \item \textbf{Сведение разнородных форматов к единой структуре.} Продажи, оплаты и банковские выписки изначально лежат в трех разных по структуре Excel-отчетах с разной иерархией (контрагент/договор/документ/номенклатура для продаж, контрагент/договор/документ для оплат, табличная часть выписки для банка). Без приведения их к единым нормализованным таблицам с одинаковыми типами полей (даты, суммы, идентификаторы) сравнивать выручку, оплаты и движение денег между собой невозможно.
  \item \textbf{Проверка полноты и согласованности.} Для банковских выписок это сверка сумм по операциям с итоговыми оборотами из шапки — без нее нельзя быть уверенным, что в выгрузку попали все операции и они не задвоены. Для продаж и оплат — проверка обязательных полей, корректности сумм и дат на уровне каждой строки. Если этого не сделать, ошибка обнаружится не на этапе загрузки, а гораздо позже — в виде необъяснимого расхождения в ДДС или аудите.
  \item \textbf{Прослеживаемость записей до источника.} Каждая строка итоговой таблицы хранит ссылку на исходный файл, лист и номер строки (\texttt{source\_*}). Это позволяет при выявлении аномалии в агрегированном отчете быстро найти конкретный первичный документ, а не пересматривать весь массив выгрузок вручную.
\end{enumerate}

Таким образом, прежде чем переходить к содержательному анализу — классификации операций, построению cash flow, оценке финансовых рисков — данные проходят обязательный этап очистки и нормализации. Его результат: воспроизводимые таблицы, для которых известно происхождение каждой строки и подтверждена арифметическая согласованность с исходными документами. Именно это позволяет доверять последующим аналитическим выводам, а не строить их на потенциально зашумленных первичных выгрузках.

\section{Общая схема обработки}

Все три пайплайна построены по единому алгоритму инкрементальной загрузки:

\begin{enumerate}
  \item в папке-источнике находятся все Excel-файлы; временные файлы Excel с префиксом \texttt{\textasciitilde\$} игнорируются;
  \item для каждого файла вычисляется SHA-256-хэш содержимого;
  \item если итоговая таблица уже существует, из нее читаются служебные поля \texttt{source\_file\_hash} и \texttt{source\_file\_path} ранее обработанных файлов;
  \item файл с уже встречавшимся хэшем пропускается повторно не обрабатывается;
  \item если файл с тем же путем изменился (хэш не совпадает), старые строки этого файла удаляются из итоговой таблицы, а файл разбирается заново;
  \item новые строки добавляются к уже накопленным данным, после чего результат целиком перезаписывается в Parquet, CSV и XLSX.
\end{enumerate}

Флаг командной строки \texttt{--rebuild} отключает инкрементальность и пересобирает итоговую таблицу из всех исходных файлов с нуля. Такая схема позволяет регулярно дозагружать новые выгрузки без повторного разбора уже обработанных файлов и без риска задвоить строки.

Каждая итоговая строка снабжается служебными полями происхождения: \texttt{source\_file} и \texttt{source\_file\_path} (имя и путь исходного файла), \texttt{source\_file\_hash} (SHA-256 файла), \texttt{source\_sheet} (лист-источник) и \texttt{source\_row\_number} (номер строки в исходном Excel). Это обеспечивает трассируемость каждой записи итоговой таблицы до конкретной ячейки исходной выгрузки.

\section{Продажи по контрагентам}

Источник: каталог \texttt{Данные/Продажи по контрагентам}, файлы формата \texttt{.xls}. Результат: таблица \texttt{sales\_by\_counterparties} (Parquet/CSV/XLSX) с гранулярностью «одна строка номенклатуры внутри документа реализации или корректировки».

Исходный отчет имеет иерархическую структуру: контрагент~$\rightarrow$~договор~$\rightarrow$~документ продажи или корректировки~$\rightarrow$~строка номенклатуры с парами дневных колонок «Количество» и «Сумма». Пайплайн проходит по этой иерархии блоками и для каждой строки номенклатуры и каждой непустой пары дневных колонок формирует одну строку итоговой таблицы.

Дата продажи (\texttt{sale\_date}) по умолчанию берется из дневной колонки Excel; если дата документа (\texttt{sales\_doc\_date}) распознана и отличается от даты колонки, используется дата документа. Это покрывает случаи, когда документ попадает в техническую колонку без явной даты.

Основные поля результата: \texttt{counterparty\_raw}, \texttt{legal\_entity}, \texttt{brand}, \texttt{store\_location\_raw}, \texttt{city\_or\_area} — контрагент и точка продажи; \texttt{contract\_raw}, \texttt{contract\_number}, \texttt{contract\_date} — договор; \texttt{sales\_doc\_raw}, \texttt{sales\_doc\_type}, \texttt{sales\_doc\_number}, \texttt{sales\_doc\_date} — документ продажи или корректировки; \texttt{sale\_date}, \texttt{nomenclature}, \texttt{quantity}, \texttt{amount} — собственно факт продажи; \texttt{period\_label}, \texttt{period\_start}, \texttt{period\_end} — отчетный период, определяемый по имени файла.

\section{Оплаты по контрагентам}

Источник: каталог \texttt{Данные/Продажи по контрагентам (по оплате)}, файлы формата \texttt{.xls}. Результат: таблица \texttt{sales\_by\_payment\_counterparties} с гранулярностью «одна строка = один платежный документ (поступление на расчетный счет)».

Структура отчета аналогична продажам, но без уровня номенклатуры: контрагент~$\rightarrow$~один или несколько договоров~$\rightarrow$~документы «Поступление на расчетный счет» с дневными колонками сумм оплат. Для каждого платежного документа и каждой непустой дневной колонки создается строка итоговой таблицы.

Дата оплаты (\texttt{payment\_date}) сначала берется из дневной колонки; если из текста документа («Поступление на расчетный счет~№~... от~...») удалось распознать дату и она отличается от даты колонки, используется дата документа. Промежуточные служебные даты в итоговую таблицу не выводятся — наружу идет только \texttt{payment\_date}.

Основные поля: \texttt{counterparty\_raw}, \texttt{legal\_entity}, \texttt{brand}, \texttt{store\_location\_raw}, \texttt{city\_or\_area}; \texttt{contract\_raw}, \texttt{contract\_number}, \texttt{contract\_date}; \texttt{payment\_doc\_raw}, \texttt{payment\_doc\_number}; \texttt{payment\_date}, \texttt{amount}; \texttt{period\_label}, \texttt{period\_start}, \texttt{period\_end}.

\section{Банковские выписки}

Источник: каталог \texttt{Данные/Выписки и данные}, файлы формата \texttt{.xlsx}, один лист «Выписка по счёту» на файл. Результат: таблица \texttt{bank\_statement\_transactions} с гранулярностью «одна строка = одна банковская операция из табличной части выписки».

Структура исходного листа: сверху — шапка выписки с реквизитами счета, периодом, входящим/исходящим остатком и итоговыми оборотами; далее двухстрочный заголовок таблицы операций; затем сами строки операций. Пайплайн определяет начало табличной части по первой строке, где значение в первой колонке распознается как дата формата \texttt{ДД.ММ.ГГГГ}, и читает только строки операций, не включая шапку в итоговую таблицу.

Исходные русскоязычные колонки переводятся в нормализованные английские имена: \texttt{operation\_date}, \texttt{document\_number}, \texttt{debit}, \texttt{credit}, \texttt{counterparty\_name}, \texttt{counterparty\_inn}, \texttt{counterparty\_kpp}, \texttt{counterparty\_account}, \texttt{counterparty\_bik}, \texttt{counterparty\_bank\_name}, \texttt{payment\_purpose}, \texttt{debtor\_code}, \texttt{document\_type}. Пустые ячейки сумм заполняются нулями. Дополнительно вычисляются два аналитических поля: \texttt{amount = credit - debit} (положительное значение — поступление, отрицательное — списание) и \texttt{direction} со значением \texttt{credit} либо \texttt{debit}.

После разбора каждого файла выполняется контрольная сверка: сумма \texttt{debit} по строкам операций должна совпадать со значением «Обороты дебет» из шапки выписки, а сумма \texttt{credit} — со значением «Обороты кредит». При несовпадении обработка файла останавливается с ошибкой, и данные из него не попадают в итоговую таблицу — это исключает попадание в анализ выписок с потерянными или задвоенными строками.
