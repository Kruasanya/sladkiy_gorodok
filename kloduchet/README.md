# КлодУчет

Реализован MVP приложения «КлодУчет» по `docs/specs/tech_spec.md` (Этапы 1–5): авторизация, организации, загрузка и обработка всех трёх типов выгрузок (продажи, оплаты, банк), четыре обязательных отчёта (продажи по времени/товарам/контрагентам, продажи и оплаты) с раскрытием до исходной строки, экспорт в Excel, Docker Compose с PostgreSQL/Redis/Celery, автотесты, резервное копирование.

## Структура

```text
kloduchet/
├── backend/          # Django + DRF API
│   ├── apps/         # organizations, imports, sales, payments, banking, analytics, exports
│   ├── pipelines/     # адаптеры к существующим *_pipeline.py из «Данные/Пайплайны обработки данных»
│   ├── config/        # settings, celery.py
│   └── venv/          # локальное виртуальное окружение (не в git)
├── frontend/          # React + TypeScript + Vite
├── scripts/           # backup.sh / restore.sh
├── docker-compose.yml  # backend, worker, frontend, postgres, redis
├── .env.example
├── docs/specs/         # функциональная и техническая спецификации
└── README.md
```

## Два способа запуска

### А. Быстрый локальный запуск без Docker (для разработки)

SQLite вместо PostgreSQL, обработка файла синхронно в HTTP-запросе вместо Celery/Redis. Модель данных, API и бизнес-логика идентичны Docker-варианту — отличается только инфраструктура.

```bash
cd kloduchet/backend
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
python manage.py migrate
python manage.py createsuperuser   # или используйте owner / kloduchet123, созданного при разработке
python manage.py runserver 8000
```

```bash
cd kloduchet/frontend
npm install
npm run dev -- --port 5173
```

Откройте `http://localhost:5173`. Vite проксирует `/api` на `http://127.0.0.1:8000` (см. `vite.config.ts`) — это важно для корректной работы кук сессии и CSRF, так как браузер не должен видеть фронтенд и backend как разные origin.

### Б. Полная схема по tech_spec.md, раздел 8 (Docker Compose)

```bash
cd kloduchet
cp .env.example .env   # заполните секреты перед реальным использованием
docker compose up --build
docker compose exec backend python manage.py createsuperuser
```

Приложение откроется на `http://localhost:3000`, backend — на `http://localhost:8000`. Контейнеры: `frontend`, `backend`, `worker` (Celery), `postgres`, `redis`. Импорт файлов в этом режиме асинхронный — `worker` забирает задачу из Redis, интерфейс опрашивает статус пакета раз в 2 секунды.

```bash
docker compose down
docker compose exec backend python manage.py migrate
docker compose exec backend python manage.py test apps
```

## Как попробовать сценарий

1. Войдите как `owner` / `kloduchet123`.
2. На странице «Организации» создайте минимум две организации.
3. На странице «Загрузка данных» выберите организацию и тип данных и загрузите файл:
   - «Продажи по контрагентам» — `.xls` из `Данные/Продажи по контрагентам/`;
   - «Продажи по контрагентам по оплате» — `.xls` из `Данные/Продажи по контрагентам (по оплате)/`;
   - «Банковские выписки» — `.xlsx` из `Данные/Выписки и данные/`.
4. Дождитесь статуса «Завершен» — приложение покажет период, число строк и сумму.
5. Откройте отчёты «Продажи по времени», «по товарам», «по контрагентам», «Продажи и оплаты» — везде доступны фильтр по организациям и экспорт в Excel.
6. Повторная загрузка того же файла для той же организации и типа завершится ошибкой «уже загружен» — проверка дублей по SHA-256.
7. На странице «Загрузка данных» завершённый пакет можно отменить — строки удалятся, файл и журнал останутся.

## Резервное копирование и восстановление (раздел 16 tech_spec.md)

При запущенном `docker compose up` (вариант Б):

```bash
cd kloduchet
./scripts/backup.sh                 # создаст backups/<дата>/ с дампом PostgreSQL,
                                     # копией data/ и MANIFEST.txt (версия + дата)
./scripts/restore.sh backups/<дата>  # восстановление из конкретной копии
```

Перед началом реальной эксплуатации обязательно проверьте восстановление на тестовом окружении.

## Автотесты

```bash
cd kloduchet/backend
source venv/bin/activate
python manage.py test apps
```

22 теста покрывают: модели и аудит организаций, выбор организации при импорте, защиту от повторной загрузки файла, откат транзакции при ошибке пайплайна, отмену пакета, права доступа (анонимный доступ запрещён), фильтры и расчёты отчётов, обязательный дисклеймер в «Продажи и оплаты», экспорт Excel. Парсинг самих Excel-файлов не тестируется здесь повторно — это ответственность уже существующих пайплайнов в `Данные/Пайплайны обработки данных`; тесты подменяют результат адаптера маленьким синтетическим набором строк (раздел 19.3 tech_spec.md: реальные финансовые файлы не должны требоваться для unit-тестов). Перед приёмкой рекомендуется отдельно прогнать реальные файлы из `Данные/` через интерфейс — это сделано вручную в ходе разработки для всех трёх типов.

## Чем демо отличается от tech_spec.md

- Раздел банковских операций как отдельный аналитический экран (12.6 п. «дополнительный экран») не реализован — банковские данные загружаются, хранятся и доступны через `/api/records/bank/`, но отдельной страницы в UI нет (по спеке это допустимо реализовать после четырёх обязательных отчётов).
- OpenAPI-схема (раздел 13) не сгенерирована автоматически — `drf-spectacular` установлен, но `SPECTACULAR_SETTINGS`/маршрут `/api/schema/` не подключены.
- Frontend component-тесты и e2e smoke-тест (раздел 19.2) не написаны — есть только `tsc -b` для проверки типов.
