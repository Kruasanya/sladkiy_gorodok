# Техническая спецификация MVP приложения «КлодУчет»

Версия: 0.1  
Статус: первый проект для обсуждения  
Дата: 21 июня 2026 года

## 1. Назначение документа

Документ определяет техническую реализацию первой рабочей версии приложения «КлодУчет» на основании функциональной спецификации `exe_spec.md` и принятых продуктовых решений.

Документ должен быть достаточен для начала разработки приложения с помощью Claude Code без дополнительных архитектурных решений со стороны исполнителя.

Если эта спецификация противоречит `exe_spec.md` в вопросах состава первой версии, приоритет для MVP имеет эта спецификация. `exe_spec.md` продолжает описывать целевой продукт.

## 2. Принятые решения

### 2.1 Формат продукта

Приложение разрабатывается как веб-приложение:

- пользователь работает через браузер на компьютере;
- frontend и backend являются отдельными частями одной системы;
- в MVP система запускается локально и бесплатно;
- после проверки MVP та же система должна разворачиваться на веб-сервере без изменения бизнес-логики и модели данных;
- в будущем допускается локальный агент, который автоматически забирает выгрузки из папок 1С и отправляет их на сервер.

Полноценное устанавливаемое desktop-приложение и мобильное приложение не разрабатываются.

### 2.2 Архитектурный подход

Используется модульный монолит:

- один backend;
- одна основная база данных;
- один frontend;
- отдельный процесс фоновой обработки;
- модули разделяются внутри кода по предметным областям;
- микросервисы в MVP не используются.

### 2.3 Технологический стек

Backend:

- Python 3.12 или более новая совместимая стабильная версия;
- Django;
- Django REST Framework;
- Celery для фоновых задач;
- Redis как брокер очереди Celery.

Frontend:

- React;
- TypeScript;
- Vite;
- готовая библиотека компонентов с поддержкой таблиц, форм, фильтров и модальных окон;
- библиотека графиков с открытой лицензией.

Хранение:

- PostgreSQL — основная рабочая база данных;
- локальная файловая система — хранение оригиналов загруженных файлов в MVP;
- Parquet — промежуточный формат существующих пайплайнов, но не рабочая база приложения.

Развертывание:

- Docker Compose;
- все используемые компоненты должны быть бесплатными и иметь открытые лицензии;
- применение обязательных платных облачных сервисов запрещено.

Конкретные версии библиотек фиксируются в файлах зависимостей при создании проекта. Следует выбирать актуальные стабильные или LTS-версии, совместимые между собой.

## 3. Цель MVP

MVP должен дать пользователю возможность загрузить имеющиеся выгрузки и получить проверяемую аналитику по продажам и оплатам.

Главный пользовательский сценарий:

1. Пользователь открывает локальное приложение.
2. Загружает исходный Excel-файл известного типа.
3. Выбирает организацию, к которой относится файл.
4. Приложение проверяет и обрабатывает файл.
5. Пользователь видит результат загрузки и контрольные показатели.
6. Загруженные данные появляются в отчетах.
7. Любую строку отчета можно раскрыть до исходной операции и исходного файла.
8. Отчет можно выгрузить в Excel.

## 4. Пользователи и права MVP

В MVP используется одна роль — пользователь системы.

Требования:

- приложение не должно допускать анонимный доступ;
- создается один локальный пользователь-владелец;
- пользователь имеет доступ ко всем организациям, загрузкам и отчетам;
- интерфейс управления пользователями и ролями не разрабатывается;
- базовая модель пользователей Django сохраняется, чтобы позже добавить администратора, роли и ограничения по организациям без замены механизма авторизации.

Регистрация через интерфейс, восстановление пароля по email, двухфакторная авторизация и корпоративный SSO не входят в MVP.

## 5. Границы MVP

### 5.1 Входит в MVP

#### Организации

- создание и редактирование двух и более организаций;
- выбор одной, нескольких или всех организаций в отчетах;
- обязательная привязка каждого пакета загрузки и каждой импортированной строки к организации.

#### Загрузка данных

Поддерживаются три существующих типа выгрузок:

1. продажи по контрагентам;
2. продажи по контрагентам по оплате;
3. банковские выписки.

Приложение принимает исходные Excel-файлы и само запускает существующий пайплайн соответствующего типа.

Также допускается техническая возможность загрузки подготовленного Parquet-файла, но основной пользовательский сценарий — загрузка исходного Excel.

#### Отчеты

Обязательные отчеты:

- продажи по времени;
- продажи по товарам;
- продажи по контрагентам;
- продажи и оплаты по контрагентам, договорам и периодам.

#### Экспорт

- экспорт текущей выборки каждого отчета в `.xlsx`;
- экспорт учитывает выбранные фильтры;
- экспортированные денежные значения должны оставаться числами, а даты — датами Excel.

#### Аудит и происхождение данных

- хранение оригинального загруженного файла;
- хранение SHA-256 файла;
- связь каждой строки с пакетом загрузки, файлом, листом, строкой и при наличии колонкой источника;
- журнал ручных изменений организаций и системных настроек;
- исходные импортированные значения нельзя редактировать через интерфейс.

### 5.2 Не входит в MVP

- ручное объединение и нормализация товаров;
- ручное объединение и нормализация контрагентов;
- точное сопоставление оплаты с конкретной реализацией;
- ручные продажи, платежи и бухгалтерские операции;
- категоризация банковских операций пользователем;
- складской учет;
- закупки;
- остатки сырья и готовой продукции;
- рецептуры;
- расчет себестоимости;
- производство;
- зарплата;
- кредиты и другие долги;
- платежный календарь;
- P&L и управленческий баланс;
- уведомления;
- отдельная административная панель продукта;
- работа без подключения к серверу;
- автоматический обмен с 1С;
- локальный агент наблюдения за папкой.

Эти функции должны учитываться при проектировании расширяемой модели приложения, но не должны реализовываться заранее.

### 5.3 Разрешение противоречия продуктовых целей и доступных данных

В качестве желаемых результатов были отмечены складские остатки и учет зарплаты. В текущих данных отсутствуют необходимые складские, закупочные, производственные и кадровые факты. Поэтому эти направления не входят в MVP, ограниченный имеющимися данными.

Движение денег технически доступно из банковских выписок. Однако в перечень обязательных отчетов MVP банковский отчет не включен, а полноценная структура расходов требует категоризации. В первой версии:

- банковские выписки загружаются и хранятся;
- корректность импорта банковских операций проверяется;
- отдельный аналитический экран банковских операций считается дополнительным и реализуется только после четырех обязательных отчетов;
- структура расходов не является критерием приемки MVP.

## 6. Исходные данные

### 6.1 Текущий объем

На дату подготовки документа:

| Набор данных | Строк | Период | Дополнительные сведения |
|---|---:|---|---|
| Продажи | 3 051 | 06.05.2025–22.06.2026 | 16 наименований, 191 исходное представление контрагента |
| Оплаты | 3 778 | 05.05.2025–17.06.2026 | 197 исходных представлений контрагента |
| Банк | 4 622 | 01.05.2025–19.06.2026 | две исходные выписки |

В продажах присутствует дата 22.06.2026, которая на момент проверки 21.06.2026 находится в будущем. До начала разработки необходимо считать это известной аномалией исходных данных, а не автоматически исправлять запись.

Ожидаемая эксплуатационная нагрузка:

- две организации;
- до десяти новых файлов в месяц;
- одновременная работа нескольких пользователей в MVP не требуется;
- текущий объем не требует отдельной аналитической базы.

### 6.2 Важное ограничение текущих таблиц

В существующих итоговых таблицах отсутствует поле организации. Поэтому:

- организация обязательно выбирается перед запуском импорта;
- организация записывается в пакет импорта;
- все строки пакета получают ссылку на выбранную организацию;
- изменение организации уже успешно импортированного пакета запрещено;
- для исправления ошибочно выбранной организации пакет необходимо отменить и загрузить заново.

### 6.3 Существующие пайплайны

Необходимо переиспользовать существующие пайплайны из каталога `Данные/Пайплайны обработки данных` в корне репозитория:

- `sales_by_counterparties_pipeline.py`;
- `sales_by_payment_counterparties_pipeline.py`;
- `bank_statement_transactions_pipeline.py`.

Бизнес-правила парсинга не следует переписывать внутри Django без отдельной причины. Пайплайны необходимо адаптировать так, чтобы их функции можно было вызывать программно, а не только как CLI-команды.

Требуемый интерфейс адаптера пайплайна:

```python
result = process_file(
    source_path=path,
    output_dir=temp_dir,
)
```

Результат должен содержать:

- путь к сформированному Parquet;
- число строк;
- контрольные суммы;
- предупреждения;
- технические ошибки;
- метаданные исходного файла.

Пайплайн не должен напрямую записывать данные в PostgreSQL.

### 7.1 Backend-модули

Backend разделяется минимум на следующие Django-приложения:

- `accounts` — пользователь и авторизация;
- `organizations` — организации;
- `imports` — файлы, пакеты загрузки, запуск и журнал обработки;
- `sales` — строки продаж;
- `payments` — оплаты из отчета 1С;
- `banking` — банковские операции;
- `analytics` — агрегирующие запросы и API отчетов;
- `audit` — история ручных изменений;
- `exports` — формирование Excel.

Запрещается создавать отдельный сервис для каждого модуля.

### 7.2 Frontend-модули

- авторизация;
- общий каркас приложения;
- глобальный фильтр организаций и периода;
- организации;
- загрузка данных;
- продажи по времени;
- продажи по товарам;
- продажи по контрагентам;
- продажи и оплаты;
- просмотр происхождения строки;
- экспорт.

## 8. Локальное развертывание

В корне проекта должен находиться `docker-compose.yml`.

Минимальные контейнеры:

- `frontend`;
- `backend`;
- `worker`;
- `postgres`;
- `redis`.

Для разработки допускается запуск frontend через dev-server Vite, а Django — через встроенный сервер разработки. PostgreSQL и Redis при этом могут работать в Docker.

Обязательные команды проекта должны быть описаны в `README.md`:

```bash
docker compose up --build
docker compose down
docker compose exec backend python manage.py migrate
docker compose exec backend python manage.py createsuperuser
docker compose exec backend python manage.py test
```

После запуска приложение должно открываться по локальному адресу без покупки домена, сертификата или облачной услуги.

Конфигурация передается через `.env`. Файл с реальными секретами не добавляется в Git. В репозитории хранится `.env.example`.

## 9. Перенос в веб после MVP

Локальная и серверная версии используют один код.

При переносе на сервер меняются:

- переменные окружения;
- адрес PostgreSQL и Redis;
- режим сборки frontend;
- файловое хранилище;
- настройки HTTPS и домена;
- политика резервного копирования.

Не меняются:

- модель данных;
- API;
- бизнес-логика;
- компоненты интерфейса;
- пайплайны обработки.

Локальная файловая система должна быть скрыта за абстракцией Django Storage. Это позволит позже перейти на бесплатное самостоятельно размещенное S3-совместимое хранилище, например MinIO, без изменения бизнес-кода.

## 10. Модель данных

Во всех таблицах используются внутренние UUID либо bigint-идентификаторы. Выбор должен быть единообразным. Для импортируемых строк рекомендуется bigint, для внешне адресуемых пакетов и файлов — UUID.

Денежные значения хранятся как `decimal`, а не `float`.

### 10.1 `Organization`

- `id`;
- `name`;
- `legal_name`, необязательно;
- `inn`, необязательно;
- `kpp`, необязательно;
- `is_active`;
- `created_at`;
- `updated_at`.

ИНН не должен быть единственным идентификатором организации, так как при первом запуске реквизиты могут быть заполнены не полностью.

### 10.2 `ImportBatch`

- `id`;
- `organization_id`;
- `data_type`: `sales`, `payments`, `bank`;
- `status`: `uploaded`, `queued`, `processing`, `validated`, `completed`, `failed`, `cancelled`;
- `original_filename`;
- `stored_file_id`;
- `sha256`;
- `file_size`;
- `period_start`, необязательно;
- `period_end`, необязательно;
- `row_count`;
- `amount_total`, необязательно;
- `debit_total`, необязательно;
- `credit_total`, необязательно;
- `error_message`, необязательно;
- `warnings` в JSON;
- `created_by`;
- `created_at`;
- `started_at`;
- `completed_at`.

Ограничение уникальности:

```text
(organization_id, data_type, sha256)
```

Повторная загрузка того же файла для той же организации и типа данных не создает новый успешный пакет.

### 10.3 `StoredFile`

- `id`;
- `storage_path`;
- `original_filename`;
- `content_type`;
- `size`;
- `sha256`;
- `created_at`.

Имя файла на диске генерируется системой и не строится напрямую из пользовательского имени.

### 10.4 `SaleRecord`

### 10.5 `PaymentRecord`

Содержит поля текущей итоговой таблицы оплат и дополнительно:

- `id`;
- `organization_id`;
- `import_batch_id`;
- все бизнес-поля `sales_by_payment_counterparties`;

- `created_at`.

Индексируются:

Содержит поля текущей итоговой таблицы банковских операций и дополнительно:

## 11. Импорт данных

### 11.1 Пользовательский процесс

1. Пользователь открывает раздел «Загрузка данных».
2. Выбирает тип данных.
3. Выбирает организацию.
4. Загружает один файл.
5. Backend сразу сохраняет оригинал и вычисляет SHA-256.
6. Backend проверяет отсутствие ранее завершенного пакета с тем же хэшем.
7. Создается `ImportBatch`.
8. Celery запускает подходящий пайплайн.
9. Пайплайн формирует временный Parquet и контрольные сведения.
10. Backend валидирует схему и значения.
11. Все строки импортируются в одной транзакции PostgreSQL.
12. Пакет получает статус `completed`.
13. Frontend показывает результат.

### 11.2 Атомарность

Выбран режим «всё или ничего»:

- если файл содержит критическую ошибку, ни одна его строка не попадает в рабочие таблицы;
- при ошибке транзакция откатывается;
- файл и журнал ошибки сохраняются;
- повторный запуск разрешен после исправления причины.

### 11.3 Проверки

Общие:

- допустимое расширение;
- ограничение размера файла через настройку;
- SHA-256;
- ожидаемые колонки результата;
- обязательные поля;
- корректность дат;
- предупреждение о датах операций, находящихся в будущем относительно момента загрузки;
- корректность числовых значений;
- число строк больше нуля;
- отсутствие бесконечных и `NaN`-значений в денежных полях;
- соответствие типа файла выбранному типу данных.

Для продаж:

- сумма `amount`;
- сумма `quantity`;
- минимальная и максимальная дата;
- наличие номера документа или исходного описания документа.

Будущая дата сама по себе формирует предупреждение, но не блокирует импорт: в исходных отчетах возможны заранее созданные документы. Пользователь должен видеть количество таких строк в результате загрузки.

Для оплат:

- сумма `amount`;
- минимальная и максимальная дата;
- наличие исходного платежного документа.

Для банка:

- сумма дебета;
- сумма кредита;
- сверка с оборотами шапки выписки;
- `amount = credit - debit`;
- соответствие `direction` знаку и заполненной стороне операции.

### 11.4 Дубли и пересекающиеся периоды

На уровне файла дубль определяется по SHA-256 в рамках организации и типа данных.

На уровне строк нельзя полагаться только на номер строки исходного файла. Для каждого типа данных необходимо рассчитывать `record_fingerprint` из стабильных бизнес-полей.

Предлагаемые составы:

- продажи: организация, тип документа, номер документа, дата документа, контрагент, договор, номенклатура, количество, сумма;
- оплаты: организация, номер платежного документа, дата, контрагент, договор, сумма;
- банк: организация, дата, номер документа, дебет, кредит, счет контрагента, назначение платежа.

Перед окончательной фиксацией fingerprint необходимо проверить реальные дубли в текущих данных. Запрещается молча удалять строки только потому, что совпало несколько полей. Система должна различать:

- повторную загрузку одного файла;
- одну операцию, попавшую в пересекающиеся выгрузки;
- две реальные одинаковые операции.

Для MVP обязательна защита от повторной загрузки одного файла. Дедупликация пересекающихся разных файлов реализуется только после подтверждения правил на реальных данных.

### 11.5 Отмена загрузки

Пользователь может отменить только полностью завершенный пакет.

Отмена:

- выполняется в одной транзакции;
- удаляет импортированные строки выбранного пакета;
- не удаляет оригинальный файл и журнал;
- меняет статус на `cancelled`;
- фиксируется в аудите.

Если строки пакета в будущем будут связаны с ручными операциями, физическое удаление потребуется заменить на логическую отмену.

## 12. Аналитика MVP

### 12.1 Общие фильтры

Каждый отчет поддерживает:

- одну, несколько или все организации;
- дату начала;
- дату окончания;
- контрагента или исходное представление контрагента, где применимо;
- товар, где применимо;
- договор, где применимо.

Период по умолчанию — текущий месяц, если в нем есть данные. Если данных нет, интерфейс должен предложить последний доступный период, а не показывать молча пустой экран.

Все суммы рассчитываются сервером. Frontend не должен самостоятельно пересчитывать финансовые итоги по загруженной странице таблицы.

### 12.2 Продажи по времени

Группировки:

- день;
- неделя;
- месяц.

Показатели:

- сумма продаж;
- количество продукции;
- сумма возвратов и корректировок;
- чистая сумма;
- изменение относительно предыдущего сопоставимого периода, если он доступен.

Отображение:

- график;
- таблица;
- строка итогов;
- раскрытие периода до документов и строк номенклатуры.

### 12.3 Продажи по товарам

Показатели:

- номенклатура;
- количество;
- сумма;
- средняя цена `sum(amount) / sum(quantity)` только при ненулевом количестве;
- доля товара в общей сумме продаж.

Корректировки с отрицательными значениями учитываются в итогах.

### 12.4 Продажи по контрагентам

Доступные уровни:

- `legal_entity`;
- `brand`;
- `counterparty_raw`;
- `contract_number`.

Показатели:

- сумма продаж;
- количество;
- число документов;
- доля в продажах;
- возвраты и корректировки.

В MVP не создается единый пользовательский справочник контрагентов. Используются значения, подготовленные существующим пайплайном.

### 12.5 Продажи и оплаты

Сравнение выполняется агрегированно, а не по конкретным документам.

Ключи сравнения:

- организация;
- исходный контрагент либо извлеченное юридическое лицо;
- договор;
- выбранный период.

Показатели:

- продажи за период;
- оплаты за период;
- разница `продажи - оплаты`;
- доля оплат `оплаты / продажи`, если продажи не равны нулю.

Разница не называется подтвержденной дебиторской задолженностью. На экране должно быть пояснение:

> Показатель является сравнением продаж и оплат за выбранный период. Он не учитывает начальные остатки, сроки оплаты и точное распределение платежей по реализациям.

При несовпадении написания контрагента или договора строки могут отображаться отдельно. Ручное объединение в MVP отсутствует.

### 12.6 Происхождение показателя

Из агрегированной строки пользователь может перейти к деталям:

- исходная операция;
- организация;
- пакет импорта;
- исходный файл;
- лист;
- номер строки;
- исходная колонка, если она сохранена.

Пользователь может скачать оригинальный файл.

## 14. Интерфейс

### 14.1 Навигация MVP

- Продажи по времени;
- Продажи по товарам;
- Продажи по контрагентам;
- Продажи и оплаты;
- Загрузка данных;
- Организации;
- выход из системы.

### 14.2 Общие требования

- основной сценарий рассчитан на desktop-браузер;
- минимальная поддерживаемая ширина основного интерфейса — 1280 px;
- интерфейс на русском языке;
- даты отображаются в формате `ДД.ММ.ГГГГ`;
- деньги отображаются с разделителями тысяч и двумя знаками после запятой;
- в таблицах есть сортировка, пагинация и явное состояние загрузки;
- пустое состояние объясняет, почему данных нет и что сделать;
- ошибки не показываются только техническим stack trace;
- длительная загрузка файла показывает текущий статус;
- экспорт доступен рядом с таблицей отчета.

### 14.3 Экран загрузки

Содержит:

- выбор организации;
- выбор типа данных;
- поле файла;
- кнопку запуска;
- список прошлых загрузок;
- статус;
- имя файла;
- период;
- число строк;
- итоговую сумму;
- время запуска и завершения;
- предупреждения и ошибки;
- действия скачать, повторить и отменить.

## 15. Безопасность

Для локального MVP обязательны:

- пароль хранится только в виде безопасного хэша Django;
- CSRF-защита для cookie-based авторизации;
- проверка типа и размера загружаемого файла;
- пользовательское имя файла не используется как путь;
- Excel-файлы не исполняются;
- пайплайн запускается без shell-интерполяции пользовательских параметров;
- секретный ключ и пароль БД находятся в `.env`;
- debug-режим отключается в серверном окружении;
- оригинальные файлы доступны только авторизованному пользователю;
- API не возвращает абсолютные пути файловой системы.

Перед публикацией в интернете дополнительно обязательны HTTPS, настройка разрешенных hosts/origins, ограничение попыток входа и регулярное обновление зависимостей.

## 16. Резервное копирование

В локальном MVP должна быть документирована ручная команда резервного копирования:

- дамп PostgreSQL;
- копия каталога оригинальных файлов;
- файл с версией приложения и датой копии.

Также должна быть документирована команда восстановления.

Автоматическое расписание резервного копирования настраивается при переносе на сервер. Проверка восстановления обязательна перед началом реальной эксплуатации.

## 17. Логирование и диагностика

Backend и worker пишут структурированные логи минимум со следующими полями:

- время;
- уровень;
- модуль;
- идентификатор запроса или задачи;
- идентификатор пакета импорта;
- сообщение;
- исключение для внутренних логов.

Пользователю показывается безопасное сообщение и идентификатор ошибки. Пароли, секреты и содержимое финансовых файлов не должны целиком попадать в логи.

## 18. Производительность

Для текущего объема:

- обычный отчет должен открываться не более чем за 2 секунды на локальном компьютере после прогрева;
- первая страница детальной таблицы — не более чем за 2 секунды;
- импорт файла выполняется в фоне и не блокирует интерфейс;
- интерфейс опрашивает статус задачи не чаще одного раза в 2 секунды либо использует более эффективный механизм;
- экспорт до 100 000 строк должен выполняться фоново, если занимает более нескольких секунд.

Предварительные агрегированные таблицы и ClickHouse в MVP не требуются. Сначала используются корректные SQL-запросы и индексы PostgreSQL.

### 19.1 Backend

Обязательны автоматические тесты:

- модели и ограничения;
- выбор организации при импорте;
- защита от повторной загрузки файла;
- успешный импорт каждого из трех типов;
- откат транзакции при ошибке;
- контрольные суммы банковской выписки;
- фильтры по организациям и датам;
- расчеты четырех отчетов;
- права доступа;
- экспорт Excel;
- отмена пакета.

### 19.2 Frontend

Обязательны:

- тесты функций форматирования и преобразования фильтров;
- component-тесты критических форм;
- end-to-end smoke-тест основного сценария:
  вход → создание организации → загрузка файла → ожидание завершения → открытие отчета → экспорт.

### 19.3 Тестовые данные

Для тестов создаются маленькие обезличенные fixtures. Реальные финансовые файлы не должны требоваться для запуска полного набора unit-тестов.

Перед приемкой выполняется отдельный интеграционный прогон на копиях текущих файлов из папки `Данные`.

## 22. Критерии приемки MVP

MVP принимается, если одновременно выполнены условия:

1. Проект запускается локально по инструкции одной командой Docker Compose после заполнения `.env`.
2. Пользователь может войти в приложение.
3. Пользователь может создать минимум две организации.
4. Можно загрузить каждый из трех известных типов исходных файлов.
5. Перед загрузкой обязательно выбирается организация.
6. Повторная загрузка того же файла для той же организации не создает дубли.
7. При ошибке ни одна строка файла не попадает в рабочие таблицы.
8. Исходный файл сохраняется и доступен для скачивания.
9. Работает фильтр по одной, нескольким и всем организациям.
10. Работают четыре обязательных отчета.
11. Итоги отчетов совпадают с контрольными расчетами по текущим итоговым таблицам.
12. Показатель продаж и оплат явно не называется подтвержденной задолженностью.
13. Агрегированные показатели раскрываются до исходных строк.
14. Каждый отчет выгружается в Excel с учетом фильтров.
15. Исходные импортированные строки нельзя изменить через интерфейс.
16. Изменения организаций фиксируются в аудите.
17. Описаны резервное копирование и восстановление.
18. Автоматические тесты проходят.

## 23. Порядок развития после MVP

Зафиксирован следующий предварительный порядок:

1. зарплата, кредиты и остальные долги;
2. закупки и склад;
3. рецептуры и себестоимость;
4. производство;
5. платежный календарь;
6. точное или полуавтоматическое сопоставление продаж и оплат.

Перед каждым этапом потребуется отдельное уточнение функциональных требований и состава доступных данных.

Технически рекомендуется перед складом и производством отдельно спроектировать модель движений и проведения документов. Реализацию зарплаты и долгов можно начать раньше, если для них будет определен ручной ввод или появятся источники данных.

## 24. Решения, которые не блокируют начало разработки

Следующие вопросы можно уточнить после создания каркаса:

- конкретная UI-библиотека React;
- внешний вид и фирменные цвета;
- нужен ли отдельный экран банковских операций в первой демонстрации;
- максимальный разрешенный размер файла;
- срок хранения отмененных оригиналов;
- нужна ли возможность загрузить несколько файлов одним действием;
- на каком бесплатном или собственном сервере размещать систему после локальной приемки;
- каким способом будущий локальный агент будет получать файлы 1С.

До отдельного решения используются простые значения конфигурации и нейтральный интерфейс.
