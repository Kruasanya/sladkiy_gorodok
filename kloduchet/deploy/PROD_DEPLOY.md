# Развёртывание Kloduchet в продакшен

Документ описывает путь от текущего дев-окружения (docker-compose с `manage.py runserver`
и Vite dev-сервером) до рабочего сайта, доступного пользователям по HTTPS.

Статус на момент написания: приложение работает только локально. Ничего из
описанного ниже ещё не сделано — это план действий, а не инструкция по
эксплуатации готового прода.

## 0. Что не так с текущей конфигурацией для прода

Зафиксировано по факту чтения [`docker-compose.yml`](../docker-compose.yml),
[`backend/config/settings.py`](../backend/config/settings.py),
[`backend/Dockerfile`](../backend/Dockerfile), [`frontend/Dockerfile`](../frontend/Dockerfile):

- `DEBUG = True` по умолчанию (`DJANGO_DEBUG` не задан) — отдаёт трейсбэки и
  внутренние пути всем посетителям.
- `SECRET_KEY` имеет захардкоженный дефолт в коде — если не переопределить
  переменной окружения, в проде будет использоваться публично видимый ключ.
- Backend запускается через `manage.py runserver` — однопоточный дев-сервер
  Django, не предназначен для реальной нагрузки. В `requirements.txt` нет
  `gunicorn`/`uvicorn`.
- Frontend запускается через `npm run dev` (Vite dev-сервер), а не как
  собранный статический бандл.
- `postgres` и `redis` публикуют порты `5432`/`6379` наружу контейнера
  (`ports:` в compose) — при разворачивании на сервере с публичным IP это
  открывает БД и брокер всему интернету.
- Нет reverse-proxy/TLS — сейчас всё ходит по HTTP на портах 8000/3000.
- `ALLOWED_HOSTS`, `CORS_ALLOWED_ORIGINS`, `CSRF_TRUSTED_ORIGINS` настроены
  только на `localhost`.
- Нет `collectstatic`/раздачи статики Django (admin, drf-spectacular UI) —
  пока работает только потому, что `DEBUG=True`.

Ничего из этого не блокирует локальную разработку — это нормально для дев-стенда.
Но всё это нужно закрыть перед тем, как пускать к приложению реальных пользователей.

## 1. Выбор хостинга

Нужен обычный VPS с Docker — Django + Celery + Postgres + Redis легко
помещаются в один сервер среднего размера (2 vCPU / 4 GB RAM хватит на старте).

Варианты: Timeweb Cloud, Selectel, VK Cloud, Yandex Cloud, Hetzner — выбор
зависит от того, где удобнее платить и где должны физически жить данные
(финансовые данные пищевого производства — соображения по локализации могут
иметь значение, уточнить отдельно).

Шаги:
1. Завести VPS (Ubuntu 22.04/24.04 LTS).
2. Установить Docker Engine + Docker Compose plugin.
3. Настроить файрвол (`ufw`): открыть только 22 (SSH), 80, 443. Всё остальное
   закрыто снаружи.
4. Завести non-root пользователя с sudo, отключить root-логин по паролю,
   входить только по SSH-ключу.

## 2. Домен и DNS

1. Купить домен (любой регистратор — Reg.ru, Cloudflare и т.п.).
2. Создать A-запись, указывающую на IP сервера (и AAAA, если есть IPv6).
3. Если используете Cloudflare как DNS — на первое время отключить проксирование
   (серое облако), чтобы Let's Encrypt мог напрямую провалидировать домен.

## 3. TLS и reverse-proxy

Рекомендация: **Caddy** вместо nginx+certbot — на порядок проще, сам выпускает
и продлевает сертификаты Let's Encrypt, конфиг — несколько строк.

Caddy становится единственным сервисом, слушающим 80/443 на хосте, и
проксирует:
- `/api/*`, `/admin/*` и т.п. → backend (Django, через gunicorn)
- всё остальное → frontend (собранные статические файлы)

Альтернатива — nginx + certbot, если в проекте уже есть опыт с nginx. Логика
та же, конфиг чуть многословнее.

## 4. Backend: подготовка к проду

1. Добавить `gunicorn` в `requirements.txt`.
2. Поменять `CMD` в `backend/Dockerfile` (или command в отдельном
   prod-compose) на `gunicorn config.wsgi:application --bind 0.0.0.0:8000 --workers 3`.
3. Добавить `whitenoise` (или раздавать `/static/` через Caddy из volume) —
   нужно для admin и drf-spectacular UI, которые сейчас держатся на `DEBUG=True`.
4. В `.env` на сервере задать:
   - `DJANGO_DEBUG=False`
   - `DJANGO_SECRET_KEY` — сгенерировать новый (`python -c "import secrets; print(secrets.token_urlsafe(50))"`),
     не использовать дефолт из `settings.py`
   - `DJANGO_ALLOWED_HOSTS=yourdomain.ru,www.yourdomain.ru`
   - `DJANGO_CORS_ALLOWED_ORIGINS=https://yourdomain.ru`
   - `DJANGO_CSRF_TRUSTED_ORIGINS=https://yourdomain.ru`
   - `POSTGRES_PASSWORD` — сгенерированный пароль, не дефолт `skladuchet`
5. Прогнать `python manage.py collectstatic --noinput` как шаг в Dockerfile
   или entrypoint перед запуском gunicorn.

## 5. Frontend: подготовка к проду

1. Собрать прод-бандл: `npm run build` (Vite положит файлы в `dist/`).
2. В проде не нужен Node.js сервер — Caddy/nginx отдаёт `dist/` как статику.
   Можно сделать multi-stage Dockerfile: стадия `node` собирает `dist/`,
   финальный образ — просто `caddy`/`nginx` с этими файлами.
3. `VITE_BACKEND_URL` на этапе сборки должен указывать на прод-адрес API
   (или фронтенд должен ходить на относительный `/api`, если Caddy
   проксирует backend на том же домене — это проще и снимает часть CORS-возни).

## 6. docker-compose.prod.yml

Завести отдельный compose-файл для прода (не трогать дев-`docker-compose.yml`):

- `postgres`, `redis` — без `ports:` наружу, только внутренняя docker-сеть.
- `backend` — без volume с исходниками внутрь контейнера (код едет вместе с
  образом при билде, не монтируется живьём), `gunicorn` вместо `runserver`.
- `worker` — без изменений в команде, но с теми же prod-переменными окружения.
- `frontend`/`caddy` — собранный `dist/` + Caddyfile, слушает 80/443.
- Volume для `data/uploads` (медиа) и для бэкапов БД.

## 7. Бэкапы

Данные финансовые — бэкапы обязательны с первого дня.

1. Cron-задача на сервере: ежедневный `pg_dump` в сжатом виде в отдельную
   директорию (не внутри контейнера — на хосте или сразу в облачное хранилище).
2. Ротация: хранить последние N дней + еженедельные на более долгий срок.
3. Желательно — копия дампов за пределами того же сервера (S3-совместимое
   хранилище, второй сервер, что угодно не-локальное).
4. Проверить процедуру восстановления один раз вручную ещё до прода, чтобы
   не выяснять, что бэкапы битые, в момент аварии.

## 8. Деплой и обновления

Вариант для старта (без CI/CD): на сервере `git pull` + `docker compose -f
docker-compose.prod.yml up -d --build`. Подходит, пока деплоит один человек
руками.

Когда станет надоедать — GitHub Actions: на push в `main` подключаться по SSH
и выполнять те же команды на сервере. Не обязательно делать сразу, можно
добавить позже без изменения остальной архитектуры.

## 9. Мониторинг и логи

Минимум для старта:
- `docker compose logs -f` — смотреть логи руками первое время.
- Настроить `restart: unless-stopped` (уже есть в дев-compose) — чтобы
  контейнеры сами поднимались после падения/перезагрузки сервера.
- Опционально позже: Sentry для бэкенд-ошибок, что-то типа Uptime Kuma для
  внешнего пинга домена.

## 10. Чек-лист перед открытием доступа пользователям

- [ ] `DEBUG=False`, новый `SECRET_KEY`, домен в `ALLOWED_HOSTS`/CORS/CSRF
- [ ] gunicorn вместо `runserver`, собранный фронтенд вместо `npm run dev`
- [ ] Postgres/Redis не торчат портами наружу
- [ ] HTTPS работает, HTTP редиректит на HTTPS (Caddy делает это сам)
- [ ] Пароли БД и Django-секрет — не дефолтные значения из репозитория
- [ ] Бэкап БД настроен и хотя бы раз проверено восстановление
- [ ] Создан суперюзер Django (`manage.py createsuperuser`) для входа в admin
- [ ] Файрвол на сервере открыт только на 22/80/443

## Открытые вопросы (нужно решить с пользователем перед началом)

- Какой хостинг-провайдер и бюджет.
- Есть ли уже купленный домен или его нужно покупать.
- Кто будет деплоить дальше — нужен ли сразу CI/CD или хватит ручного деплоя.
- Требования к локализации данных (где физически должна жить БД).
