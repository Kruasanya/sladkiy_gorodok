\chapter{Подготовка данных и классификация банковских операций}

\section{Постановка задачи и обоснование подхода}

Банковская выписка является наиболее честным и полным первичным источником информации о денежных потоках предприятия: в отличие от управленческого учёта, она не содержит начислений без оплаты и фиксирует реальное движение денег. Вместе с тем сырая выписка бесполезна для финансового анализа: строки вида «оплата по счёту 1254 от ООО Прогресс» или «пл. по дог. б/о» не несут управленческой информации о природе платежа.

Задача классификации банковских транзакций по экономическому содержанию является частным случаем задачи категоризации коротких текстов~\cite{aggarwal2012survey}. В классической постановке она решается методами NLP: наивным байесовским классификатором, методом опорных векторов на TF-IDF признаках~\cite{sebastiani2002machine}, а в последние годы --- предобученными трансформерами типа BERT~\cite{devlin2018bert}. Однако в условиях малого бизнеса задача имеет несколько особенностей, которые определяют выбор методов:
\begin{enumerate}
  \item \textbf{Высокая доля структурированных паттернов.} Назначения налоговых платежей, кредитных выплат и банковских комиссий имеют почти стандартизированные формулировки, поддающиеся регулярным выражениям.
  \item \textbf{Небольшое число уникальных контрагентов.} В выборке из 4\,086 операций насчитывается лишь около 70 уникальных контрагентов; многие из них однозначно идентифицируются по имени или ИНН.
  \item \textbf{Отсутствие размеченного обучающего набора.} Для обучения полноценного ML-классификатора необходима разметка, которой изначально нет.
  \item \textbf{Требование интерпретируемости.} Финансовый аудит требует проверяемости каждого решения: автоматическая классификация должна объяснять причину присвоения категории.
\end{enumerate}

Исходя из этого, в проекте принята многоуровневая стратегия: \textit{rule-based} классификация как основной метод, \textit{LLM-разметка} как вспомогательный сигнал для неоднозначных назначений и ручная валидация выборки для оценки качества.

\section{Источники данных и ETL-пайплайны}

\subsection{Структура источников данных}

В проекте используются три типа источников данных:
\begin{enumerate}
  \item \textbf{Банковские выписки} по расчётному счёту предприятия (формат Excel, экспорт из интернет-банка). Структура файла: шапка с периодом, владельцем счёта, остатками и оборотами; двухстрочный заголовок таблицы; строки операций.
  \item \textbf{Продажи по контрагентам} --- отчёты 1С о реализации и корректировках (Excel). Иерархическая структура: контрагент $\to$ договор $\to$ документ (реализация / корректировка реализации) $\to$ строки номенклатуры.
  \item \textbf{Продажи по оплатам} --- отчёты 1С о поступлениях на расчётный счёт (Excel). Структура: контрагент $\to$ договор $\to$ платёжный документ.
\end{enumerate}

\subsection{Инкрементальные пайплайны обработки}

Для каждого источника реализован воспроизводимый ETL-пайплайн на Python. Все три пайплайна работают по единой инкрементальной логике:
\begin{enumerate}
  \item Найти все исходные Excel-файлы в исходной папке (игнорируя временные файлы \texttt{$\sim$\$*}).
  \item Вычислить SHA-256 хэш каждого файла.
  \item Если итоговый CSV уже существует, прочитать из него поля \texttt{source\_file\_hash} и \texttt{source\_file\_path}.
  \item Если файл с таким хэшем уже обработан --- пропустить.
  \item Если файл с тем же путём изменился --- удалить старые строки и перепарсить.
  \item Добавить новые строки к итоговой таблице.
  \item Сохранить результат в форматах Parquet, CSV и XLSX.
\end{enumerate}

SHA-256 хэширование гарантирует, что при повторном запуске пайплайна уже обработанные файлы не будут дублированы. Флаг \texttt{--rebuild} отключает инкрементальность и пересобирает таблицу с нуля.

Пайплайн банковской выписки дополнительно выполняет \textbf{проверку оборотов}: суммарные значения \texttt{debit} и \texttt{credit} по строкам сверяются с полями «Обороты дебет» и «Обороты кредит» из шапки выписки. При несовпадении пайплайн останавливается с ошибкой --- это гарантирует целостность финансовых данных.

\subsection{Поля итоговой таблицы банковских операций}

Итоговая таблица \texttt{bank\_statement\_transactions} включает следующие ключевые поля: \texttt{operation\_date} (дата операции), \texttt{document\_number} (номер платёжного документа), \texttt{direction} (\texttt{credit} / \texttt{debit}), \texttt{amount} (= credit $-$ debit), \texttt{counterparty\_name}, \texttt{counterparty\_inn}, \texttt{counterparty\_kpp}, \texttt{payment\_purpose} (назначение платежа, свободный текст), а также служебные поля \texttt{source\_file}, \texttt{source\_file\_hash}, \texttt{source\_sheet}, \texttt{source\_row\_number} для аудита происхождения каждой строки.

\section{Очистка и дедупликация банковской выписки}

\subsection{Объединение пересекающихся выписок}

Банковские выписки были предоставлены в виде двух файлов с пересекающимися периодами:
\begin{itemize}
  \item выписка за 01.05.2025--30.04.2026: 4\,086 строк операций;
  \item выписка за 01.06.2025--09.05.2026: 3\,970 строк.
\end{itemize}

При наивном объединении возникло бы \textbf{8\,056 строк}, из которых около половины --- дублирующийся период. Применение стандартной дедупликации по паре (дата, сумма, контрагент) неприменимо: два платежа одному поставщику на одинаковую сумму в один день могут быть \textit{разными} реальными операциями.

В проекте применена стратегия дедупликации по \textbf{полному набору семи полей}: \texttt{operation\_date}, \texttt{document\_number}, \texttt{counterparty\_inn}, \texttt{amount}, \texttt{payment\_purpose}, \texttt{counterparty\_account}, \texttt{document\_type}. Строки, идентичные по всем перечисленным полям и попавшие в базу из пересекающихся файлов, удаляются как технические дубли. Результат дедупликации:
\begin{itemize}
  \item точных дублей строк: 0;
  \item групп натуральных дублей (одинаковых по 7 ключевым полям): 3\,866;
  \item удалено технических дублей: 3\,866;
  \item осталось операций для анализа: \textbf{4\,086}.
\end{itemize}

\subsection{Парсинг дат}

Банковские выгрузки в формате Excel нередко содержат даты в смешанных форматах: числовой код Excel («серийный номер»), строка в формате \texttt{DD.MM.YYYY} или \texttt{YYYY-MM-DD}, либо \texttt{NaT} как артефакт парсинга pandas.

Реализована специализированная функция \texttt{parse\_bank\_dates}, последовательно применяющая:
\begin{enumerate}
  \item преобразование числового кода через \texttt{xlrd.xldate\_as\_datetime};
  \item разбор строки по шаблонам \texttt{DD.MM.YYYY} и \texttt{YYYY-MM-DD};
  \item контекстную интерполяцию по соседним строкам.
\end{enumerate}

После применения функции число операций без корректно распознанной даты: \textbf{0}.

\subsection{Нормализация назначений платежей}

Назначение платежа --- свободный текст, заполняемый отправителем произвольно. Для rule-based классификации необходима нормализация:
\begin{itemize}
  \item приведение к нижнему регистру;
  \item удаление лишних пробелов и специальных символов;
  \item унификация частых аббревиатур (дог.\ $\to$ договор, б/о $\to$ без объекта);
  \item выделение ключевых токенов по регулярным выражениям.
\end{itemize}

\section{Разработка строгого справочника категорий}

\subsection{Принципы построения таксономии}

Разработка справочника категорий --- один из ключевых этапов: без чёткой таксономии автоматическая классификация лишена смысла. В проекте разработан список из \textbf{17 укрупнённых категорий} без смысловых пересечений. Принципы:

\begin{enumerate}
  \item \textbf{Взаимная исключительность.} Каждая операция относится ровно к одной категории.
  \item \textbf{Соответствие типу операции.} Для каждой категории задан допустимый тип: \texttt{credit} (поступление) или \texttt{debit} (списание). Это исключает классификационные ошибки ещё до финального сохранения.
  \item \textbf{Разделение категорий и подкатегорий.} Детализация (конкретный вид сырья, тип налога) выносится в поле \texttt{subcategory}.
  \item \textbf{Управленческая интерпретируемость.} Категории напрямую соответствуют строкам управленческого ДДС.
\end{enumerate}

\section{Rule-based классификатор}

\subsection{Принцип работы и иерархия правил}

Rule-based подход --- упорядоченный набор правил, применяемых последовательно в порядке убывания специфичности~\cite{Cohen1995}. Он прозрачен: для каждой операции можно точно объяснить причину присвоения категории, что принципиально важно в финансовом аудите.

Классификатор проверяет паттерны в полях \texttt{payment\_purpose}, \texttt{counterparty\_name} и \texttt{counterparty\_inn}, а также тип операции \texttt{direction}. Иерархия правил организована в пять уровней:

\textbf{Уровень 1 --- детерминированные идентификаторы.} Операции, однозначно определяемые по ИНН:
\begin{itemize}
  \item ИНН налоговой инспекции $\to$ «Налоги, взносы, штрафы»;
  \item ИНН ПФР / СФР / ФСС $\to$ «Налоги, взносы, штрафы».
\end{itemize}

\textbf{Уровень 2 --- семантические паттерны в назначении.} Примеры регулярных выражений:
\begin{itemize}
  \item \texttt{/зарплат|аванс\textbackslash b|подотчёт|отпускн/i} $\to$ «Персонал»;
  \item \texttt{/мука|сахар|меланж|сгущ|молокосодерж|яичн|масло\textbackslash s+раст/i} $\to$ «Закупки для производства»;
  \item \texttt{/упаковк|пакет|плёнк|стрейч|лоток|коробк/i} $\to$ «Упаковка и расходники»;
  \item \texttt{/аренд|коммун|электроэнерг|водоснабж|вывоз\textbackslash s+отходов/i} $\to$ «Аренда и коммунальные»;
  \item \texttt{/погашение\textbackslash s+кредит|процент\textbackslash s+по\textbackslash s+кредит|аннуитет/i} $\to$ «Кредиты и займы»;
  \item \texttt{/ОПЛАТА ЗА ТОВАР|ПОСТУПЛЕНИЕ НА РАСЧЕТНЫЙ СЧЕТ|ПО ДОГОВОРУ ПОСТАВКИ/} $\to$ «Выручка от клиентов» (\texttt{credit}).
\end{itemize}

\textbf{Уровень 3 --- контрагентные словари.} Справочник контрагентов, классифицированных по юридическому лицу:
\begin{itemize}
  \item ООО «Меланж», ООО «РАДУГА Н», АО «ТУЛАХЛЕБОПРОДУКТ» $\to$ «Закупки для производства»;
  \item ООО «ТК «Шебекинский Картон»» $\to$ «Упаковка и расходники»;
  \item ИП Баскаков С.А.\ $\to$ «Аренда и коммунальные платежи»;
  \item ООО «Тензор», ООО «Бизнес-Софт», ПАО «Ростелеком» $\to$ «Связь, сервисы и подписки»;
  \item ООО «Эко-Сфера», ООО «Хартия» $\to$ «Аренда и коммунальные платежи» (вывоз отходов).
\end{itemize}

\textbf{Уровень 4 --- широкие правила.} Кредитовые операции от юридических лиц, не подпавшие под уровни 1--3, $\to$ «Выручка от клиентов» с уверенностью \texttt{medium}.

\textbf{Уровень 5 --- unknown.} Операции, не подпавшие ни под одно правило.

\subsection{Управление уверенностью и флаги проверки}

Каждому правилу присвоен уровень уверенности: \texttt{high} ($\geq 0{,}90$), \texttt{medium} ($0{,}70$--$0{,}89$) или \texttt{low} ($< 0{,}70$). Операция помечается флагом \texttt{needs\_review~=~True} при:
\begin{itemize}
  \item уверенности ниже 0{,}70;
  \item категории unknown;
  \item расхождении между rule-based и LLM результатами;
  \item сумме, входящей в топ-5\% по абсолютному значению (крупные нетиповые платежи).
\end{itemize}

\section{LLM-разметка как дополнительный сигнал}

\subsection{Мотивация и ограничения LLM}

Большие языковые модели (LLM) показывают высокую эффективность в задачах классификации коротких текстов с нестандартными формулировками~\cite{brown2020language}. В финансовом контексте LLM способна интерпретировать деловой жаргон, аббревиатуры и неполные описания, которые rule-based классификатор относит в unknown.

Применение LLM к банковским данным требует особой осторожности с точки зрения конфиденциальности. В данном проекте используется \textbf{локально развёрнутый LLM-сервер} (LM Studio) с открытой моделью, что исключает передачу финансовых данных во внешние сервисы.

Характерное ограничение LLM --- склонность к «галлюцинациям»: возврату произвольных категорий, не входящих в допустимый список~\cite{ji2023survey}. Для предотвращения этого каждый запрос строго ограничен перечнем допустимых категорий и требует ответа в формате JSON.

\subsection{Архитектура промпта}

Промпт для LLM-классификации содержит следующие элементы:

\begin{enumerate}
  \item \textbf{Системная инструкция}: «Ты финансовый классификатор банковских операций малого производственного бизнеса. Нужно выбрать ровно одну \texttt{category} из списка и одну \texttt{subcategory}. Не объясняй ход рассуждений. Верни только валидный JSON.»
  \item \textbf{Ограничения}: полный список 17 допустимых категорий; явные правила для типов операций (\texttt{credit} / \texttt{debit}); запрет выбора расходных категорий для поступлений и наоборот.
  \item \textbf{Контекст операции}: тип (\texttt{credit} / \texttt{debit}), наименование контрагента, назначение платежа.
  \item \textbf{Требуемый формат}: \texttt{\{"category": "...", "subcategory": "...", "confidence": 0.X\}}.
\end{enumerate}

\subsection{Итоговая схема классификации}

Финальная категория (\texttt{category\_final}) формируется по логике с приоритетом:
\begin{itemize}
  \item если \texttt{rule\_confidence} $\geq 0{,}90$ и категория валидна для типа операции $\to$ приоритет rule-based;
  \item если rule вернул unknown или \texttt{low} и LLM дал валидный результат $\to$ используется LLM;
  \item при расхождении между rule и LLM при уверенности \texttt{medium} $\to$ операция помечается \texttt{needs\_review} с \texttt{review\_reason = "rule\_llm\_disagreement"}.
\end{itemize}

\subsection{Ручная валидация}

Для оценки качества подготовлена валидационная выборка из \textbf{500 операций} (\texttt{outputs/manual\_validation\_500.xlsx}). Выборка стратифицирована по типу операции и категории; в неё включены все 238 операций с флагом \texttt{needs\_review}.

В файле вручную заполняются поля \texttt{category\_manual} и \texttt{subcategory\_manual}. После завершения разметки автоматически рассчитываются метрики согласованности: accuracy, macro-F1 и матрица ошибок для каждой пары (\texttt{category\_rule} vs \texttt{category\_manual}), (\texttt{category\_llm} vs \texttt{category\_manual}), (\texttt{category\_final} vs \texttt{category\_manual}).

Такой подход согласуется с рекомендациями по валидации автоматической разметки в отсутствие золотого стандарта~\cite{pustejovsky2012natural}: ручная разметка выборки позволяет оценить качество алгоритма без полной ручной разметки всего датасета.

Итоговый результат этапа: unknown практически устранён (0,01\% оборота), структура расходов и поступлений прозрачна, данные пригодны для построения управленческого cash flow и обучения прогнозных моделей.
